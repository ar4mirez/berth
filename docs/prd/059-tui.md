# PRD: `berth tui`, an interactive dashboard (#59)

Status: **done** · Issue: [#59](https://github.com/ar4mirez/berth/issues/59) · Restarts orgs: no

## Problem

berth has everything a dashboard needs (hosts, orgs and their state, Remote Control, firewall, repos, backups,
logs) and shows it one command at a time. Many operators prefer one screen.

## Decisions (2026-10-07; mine, the issue left them open)

- **Bubble Tea** (v1) with Lip Gloss, as the issue suggests. No component library: the list, tabs, prompt and
  dialogs are small enough to own, and that keeps the dependencies to those two.
- **Actions in this version:** start, stop, restart; firewall allow and deny; repo add, remove, sync; back up now;
  attach and shell. Not: creating and destroying orgs, sign-ins, setting variables (a secret would be typed into
  the dashboard), packages, migration, host management.
- **Confirmation is a `y`**, with `enter` and everything else cancelling, after a box that says what the operation
  does and what stops. Typing the org's name, as the MCP server asks of an agent, is for a caller that can't see.
- **Log follow is a tail read again** every few seconds, through `ops.TailLogs`, not a stream.
- **attach and shell run berth itself** with the terminal (released with `tea.Exec`, started through berth's own
  process layer), so they behave as the commands do.

## Design

- **`internal/tui`**: a `Backend` interface (what the dashboard reads and does), a model, and views.
  - The real backend is the operations layer on an App: `ops.ListOrgs`, `GetHosts`, `GetInfo`, `GetFirewall`,
    `GetRepos`, `GetEnv`, `GetPackages`, `ListBackups`, `TailLogs` for reading; the commands' own code (`App.Up`,
    `Fw`, `Repo`, `Backup`) for acting, with its output captured. There is no other logic.
  - **Every action is `(Cmd, Sub)` in `ops.Catalog`, and one function gates them all** (`Model.request`): a write
    is refused under `--read-only`; `Restart != Never` needs the confirmation, whose text is the catalog's note;
    the two that remove something ask too. Only `request` and a confirmed confirmation reach `run`.
  - Messages are respelled for berth's command line (`ops.Respell`).
- **`berth tui`** in the CLI, in the catalog as a read. It refuses without a terminal.
- Sizes: it draws in 40×10 and up, clips every line to the width and the page to the height, and keeps a default
  size when the terminal doesn't report one.
- Themes: adaptive colours (light and dark), and plain text when the terminal has no colour.

## Acceptance criteria

| Criterion (from the issue) | How it is checked |
|---|---|
| Every view reads through the operations layer; there's no separate logic | `backend.go` calls only `internal/ops` reads and the commands' own methods; the views take `ops` documents |
| Snapshot tests for the main views | `TestViews`: 15 views against `testdata/*.txt`, plus width and height limits |
| Restart actions can't run without confirmation (tested) | `TestRestartsNeedConfirmation`: for each of up, down and restart, six answers that aren't `y` run nothing; `y` runs it once; the box names what stops, in the catalog's words |
| `--read-only` works in the TUI | `TestReadOnly`: eight writes and handoffs refused, nothing run, reading goes on |
| Documented, with a screenshot or recording | `docs/guides/tui.md`, with the views as text, taken from the snapshots |

## Not done

- **A recording or image** in the docs: the guide shows the screens as text, which is what the snapshot tests hold.
- **Mouse.** The issue calls it optional.
- **Each org's image** in the list: the orgs document doesn't carry it.
- **Progress while an action runs:** the header says what is running; its output shows when it ends.
